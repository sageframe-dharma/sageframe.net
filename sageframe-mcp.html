v0.2 · read-only slice · MCP over stdio
Homelab operations as typed tools

Knowledge that should live once, living somewhere callable.

The skills are the strategy. This is the move set.

A local MCP server that exposes a personal homelab as deterministic, typed tools — so any Claude session can ask which hosts exist, what runs where, and what's quietly broken, and get structured data back instead of re-deriving SSH commands from documentation every time.

// the problem

Documentation is a thing you read. Not a thing you call.

A homelab accretes knowledge the way any real system does: across skill files, reference docs, an SSH config, a deploy runbook, a half-remembered incident. The execution paths are written down — but documentation has to be read and translated on every use, and translation is lossy and repeated.

The host inventory alone lived in five separate sources that disagreed with each other — one of them still pointing at an IP that had moved months earlier. Five mirrors of one truth, quietly drifting. Every new session paid the tax of reconciling them by hand.

The fix isn't better documentation. It's turning the executable parts into verbs — encoded once, called deterministically, returning data the agent can reason over rather than a text blob it has to parse.

// the idea

Skills teach when. The MCP guarantees how.

The interesting move is a separation of concerns most infrastructure tooling collapses. The skills stay authoritative for judgment — whether and when to act. The MCP owns mechanism — the exact command, path, and flag, executed the same way every time. Strategy and execution stop being tangled in the same prose.

strategy layer

The skills

Teach an agent how to think about the homelab — when a deploy is warranted, why a mount gets verified before a backup, which host earns a service. Judgment, not verbs.

execution layer

The MCP

Encodes the mechanical parts as callable tools. One tool call returns a typed model — deterministic, testable, impossible to get subtly wrong the way a hand-copied command is.

// why it's interesting

Four things it gets right that generic tools don't.

01

It is deliberately not generic.

Generic infrastructure MCP servers exist. They don't know that one host needs a jump, that another's sudo wants an interactive password, that a third is off-site on a tailnet, or that a past data-loss incident is why a verification gate exists. This project's entire value is that it encodes a specific topology and specific hard-won rituals — the parts a generic tool can never carry.

02

It reflects truth — it never authors it.

The server reads a single hand-authored inventory and probes live state. It never mutates the source of truth. Reads come first; writes are staged behind them, gated three ways, and never the default. The design makes "reflected truth" safe over time by structurally refusing to become a fourth place the truth can drift to.

03

Structured data in, structured data out.

Tools return Pydantic models, not shell output. "What's quietly broken" is one fan-out call surfacing failed units across every host as typed records — something an agent can act on directly, rather than a wall of text it has to re-parse and hope it read correctly.

04

It's a worked example of a method.

The whole thing was built under the Ho System discipline — a documented chain from seed to system design to build sequence, each session bounded and planned before any code was written. The repository is as much a demonstration of how to build a real tool deliberately as it is the tool itself.

// the method

Nothing here was improvised.

Every decision has a paper trail. The architecture was committed before the first line of code; each working session opened against a single bounded document and closed when its deliverable was done. Earlier decisions stay on the record rather than being quietly rewritten — the history of what the project believed at each step is preserved, not laundered.

The verification stack runs at every commit: lint, strict type-checking, and a test suite held above a 90% coverage floor, enforced by pre-commit hooks. The discipline isn't ceremony — it's what lets a homelab tool be trusted to say what's true about the machines it touches.

seed→ system design→ README→ ho sequence→ per-ho builds
// technical footprint

Small, sharp, and honest about its edges.

Roughly ten source modules doing exactly what they claim. The SSH executor is a thin, well-tested subprocess layer over OpenSSH that honors the existing config as the single source of connection truth — no key handling, no cleverness. When a host needs a privilege the tool can't grant non-interactively, it surfaces a structured error saying so, rather than pretending.
